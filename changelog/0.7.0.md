# S++ 0.7.0

## Debugging and crash reports

- **Programs carry line tables:** every module gets DWARF line tables: a compile unit per module, a subprogram per
  function, closure and coroutine, and a location on every statement. gdb and lldb can break on a line of a `.spp` file
  and step through it, and show each frame's file and line, inlined frames included. Code the compiler makes itself is
  artificial, at line 0, so a debugger steps over it.

- **Variables and their types:** with full debug info, every parameter (`self` included) and every binding is described
  with its type, so a debugger shows their values: numbers, `Bool`, borrows and pointers, arrays, classes and tuples
  with their fields at their real offsets, and variants as their tag and payload. Types are named as S++ writes them,
  with their module path (`std::vector::Vec[S32, std::allocator::GlobalAlloc]`, `(U64, Bool)`,
  `std::option::None or std::option::Some[S32]`). Each block is its own scope, so a name shadowed inside a block shows
  the inner
  binding there, and a block's variables are gone after it; compiler temporaries (`$temp...`) are not shown. A
  binding moved away shows as not available from the move (gdb's `<optimized out>`, lldb's `<variable not available>`)
  until it is given a new value, rather than the bytes it no longer owns, and before its `let` has given
  it one; this is debug info only, the code is unchanged. A partial move (one field moved out) still shows the whole
  binding.

- **Stepping follows the code that runs:** the code after a block (a `case` storing its value) is at the statement's
  own line, so stepping out of the branch taken no longer stops on the one not taken. "Step into" stops in std code as
  anywhere else. Known: at dev, gdb stops twice on a line with checked arithmetic (once before and once after the std's
  inlined add); lldb stops once.

- **Debugger formatters for std's types** (`SPP-STL` `etc/gdb/spp_std.py` and `etc/lldb/spp_std.py`, loaded by the
  CLion plugin, or by hand with `source` or `command script import`) show them by their contents: `"héllo"`,
  `Vec(len=2, cap=2)` with its elements, `Some(7)` and the member any variant holds, `'é' (U+00E9)`, `Single(5)`,
  `Rc(6, strong=2, weak=1)`, `Mutex(10)`, `BigInt(-12345678901234)`, `Duration(1.5s)`, a `TimePoint` as a UTC date,
  and `Path("src/main.spp")`. One-byte integers show as numbers, not characters. Checked in gdb and lldb by
  `tests/codegen/check-debug-formatters.sh`, and by hand in CLion's bundled LLDB.

- **`[binary.debug] info`** (`"full"`, `"lines"` or `"none"`) chooses this: full debug info at dev and line tables at
  rel when it is not set. `"none"` gives the same code and IR as before, and the others leave the machine code as it
  is: only the binary grows (`./project`'s dev executable from 131 KB with lines to 189 KB with full). Any other value
  is refused when `spp.toml` is read, naming the values allowed. Full debug info with the split stack is costly in
  huge functions (a generated one with 31,000 variables took 3.5 GB to compile), and loses the variables
  SafeStack moves: LLVM tracks each one instruction by instruction, on a register. Fixed upstream in
  [llvm/llvm-project#242016](https://github.com/llvm/llvm-project/pull/242016) (open); until spp builds against an
  LLVM with it, build for a debugger with `--for-debugger`.

- **Crash reports name source lines:** a failed check, an abort and a fatal signal print `at file:line:column` under
  each frame, and each call inlined into it, innermost first, with the function it is in:

  ```
    #0  main::bump+0x1f  (lines)
            at vcs/std/src/std/intrinsics.spp:25:1  (inlined std::intrinsics::uadd[T=SizedInteger[8_u32, false]])
            at vcs/std/src/std/num/sized_integer_unsigned.spp:33:5  (inlined std::num::sized_integer_unsigned::add[w=8_u32])
            at src/main.spp:6:3
  ```

  The compiler builds a source-line table from the program's own DWARF, and links it in beside the program's object
  (`out/<target>/<mode>/llvm/spp-lines.o`). The runtime reads it without parsing any debug format, so the same report
  works on every platform whose objects carry DWARF. A stripped program has no symbol names left, so its frames have no
  lines either. An MSVC target emits CodeView rather than DWARF, so its table is empty for now.

- **A failed check keeps its own line:** with debug info, the check-failure call in the runtime is not merged with
  another, so each check reports its own line, rather than one shared by several or none.

- **A debugger stops on a failure:** a failed check or an abort ends the process with `_exit`, which a debugger saw only
  as an exit. The runtime now calls `sppc_debug_fatal` first, once the report is written, as Rust's tooling breaks on
  `rust_panic`, so a breakpoint on it stops with the failing code's frames still on the stack.

- **Source paths are relative to the project** in the debug info (`src/main.spp`, with the compile directory `.`), so
  a build records nowhere it was built, and stays byte-for-byte reproducible. Run the debugger from the project's
  directory, or map `.` to it (`set substitute-path` in gdb, `target.source-map` in lldb).

## Language

- **`##` is an ordinary comment (breaking):** it was a block comment, running to the next `##`, whose line breaks the
  lexer dropped, so every line after one had the wrong number. It is now a line comment like any other `#`: a block
  written with it must have `#` on every line. A string literal can still span lines.
- **A program reads its arguments with `std::process::args()`** (`SPP-STL`), the program's own name first, as Rust's
  `std::env::args()`. `main` still takes none: the C entry point the compiler makes hands `argc` and `argv` to the
  runtime first. On Windows the runtime splits the UTF-16 command line itself into UTF-8, as the C runtime library's own
  `argv` is in the ANSI code page and garbles anything else.

## Command line

- **`spp run -- <args>`** passes everything after `--` to the program, each argument whole: spaces, quotes and `$` are
  not split or expanded. An option before `--` that `spp run` does not know is still refused.
- **`spp build --for-debugger`** builds a program for a debugger to run: the split stack (`[memory.stack] split`) is
  left
  out unless spp.toml sets it, and recorded as left out, as LLVM loses track of the variables it moves (they show as
  optimised out, or wrong). spp-idea's Debug builds with it. It goes once the LLVM fix above is released.
- **`spp info executable`** (new `spp info` command) prints the absolute path the executable is built to for the mode
  and target (`-m`, `-t`), on a line of its own, and builds nothing. It is for a tool or script that starts the
  program itself, such as an IDE's debugger (`gdb "$(spp info executable)"`). A library has no executable, so it fails
  and prints nothing.
- **`spp self update`** replaces the running `spp` with the latest release for its platform: it finds the latest release
  (from GitHub's `releases/latest` redirect, with no API or rate limit), downloads that release's `spp-<platform>.zip`
  and `SHA256SUMS` with `curl`, checks the zip against its checksum, unpacks it (`unzip` on Linux, which it needs
  installed; `tar` on macOS and Windows) and moves the new `spp` over the old one. It says so and changes nothing when
  this `spp` is the latest already, or newer; and refuses, changing nothing, a download that does not match, a directory
  it cannot write to, and an install Homebrew or Nix manages. `--version X` installs the release named instead, up or
  down; one before 0.7.0, or with no release, is refused. 0.7.0 is the first release it can update from: the first in
  the zipped form it downloads. `SPP_UPDATE_BASE_URL` points it at another server laid out as GitHub's releases, for
  testing.
- **`spp self install`** installs the `spp` it is run from: it copies it to `~/.spp/bin` (`%LOCALAPPDATA%\spp\bin`
  on Windows, or `--dir`) and puts that on `PATH` for new terminals, through `~/.spp/env`, read from each shell
  start-up file there (one line, and a fish snippet where fish is set up), or the user `Path` on Windows. A
  download then needs one step: unzip, `./spp self install`, and `spp self update` keeps it current. It stops, changing
  nothing, when it is installed there already, a different `spp` is there, or another is on `PATH`; `--force` goes
  ahead. `--no-modify-path` leaves `PATH` alone. Nothing else needs it: `spp` runs wherever it is.
- **`spp self uninstall`** removes the running `spp` once confirmed (`--yes`, or "y" to its question; no answer removes
  nothing), with what `spp self install` set up for it (its `PATH` changes, and `~/.spp` once empty), and says what it
  leaves: each project's `vcs` and `out` folders. It refuses an install Homebrew or Nix manages, as `spp self update`
  does.
- **`spp build --message-format=json` names what it linked:** a successful build of an executable ends with
  `{"kind":"artifact","executable":"<absolute path>"}`, so a tool reading the json needs no second call to find it.

## Hardening

- **Windows has no split stack:** SafeStack names its thread-local unsafe stack pointer from the program, and the
  runtime that defines it is a DLL on Windows, which cannot export a thread-local, so the link failed with an undefined
  symbol. `[memory.stack] split`, on by default, is now left out on Windows (and on any target without an unsafe stack
  pointer, or without a canary for it beside `protect`), and is recorded as left out. A default `pac_ret` that rests on
  it is left out with it. Either set explicitly to `true` still fails the build, naming the reason. CI no longer turns
  both off by hand for the Windows lanes.

## Fixed

- **A variant of a class from a later module could be too small for its value (memory corruption):** a class used before
  its own module was compiled (through a constant of an array of it, say) was sized while still an empty placeholder,
  and LLVM cached that empty layout for the rest of the module. In `./project`, `Opt[BigInt]` came out with a 0-byte
  payload, so storing a `BigInt` in it overran the stack ("stack smashing detected"), and `BigInt` was read and
  written with alignment 1. Such a class is now laid out when it is first needed, whichever module that is.
- **Error messages counted lines differently from an editor:** a line break inside a string literal did not end a line,
  so a message about code after a multi-line string named the wrong line and quoted the wrong source. Lines are now
  counted as the file is written, and the whole-file span ends on the file's last line rather than one past it.
- **The Windows console** shows the progress bar and coloured errors correctly: it is switched to UTF-8 at startup.

## Runtime and std

These ship in SPP-STL (`ffi/sppc` and `src/std`), which a project fetches into `vcs/std`; a build with `info = "lines"`
needs an SPP-STL whose runtime has `sppc_set_source_lines`, and every program one with `sppc_set_args`.

- **Debugger formatters** for std's types, in `etc/gdb/spp_std.py` and `etc/lldb/spp_std.py` (see Debugging), beside
  the layouts they read, so they change with them.
- **sppc:** the source-line table reader (`sppc_set_source_lines`), `sppc_debug_fatal`, and the program's arguments
  (`sppc_set_args`, `sppc_arg_count`, `sppc_arg_len`, `sppc_arg`), read at their exact length.
- **`std::process::get_env`** reads a value of any length: it read into a 1024-byte buffer, and a longer value came back
  as `None`, as though the variable were not set. The buffer is sized by `sppc_getenv_len`, in the runtime.
- **`std::process::set_env` and `unset_env`** passed their name and value to C without a terminator, so C read past
  their end: `set_env` set a variable under a name that ran on into the program's other strings, and `unset_env`
  removed one of the same kind. Both now terminate them, as `get_env` did.

## Releases

- **Each platform's release is a zip** (`spp-linux-x64.zip`, `spp-linux-arm64.zip`, `spp-macos-arm64.zip`,
  `spp-windows-x64.zip`) holding `spp` or `spp.exe` under its plain name, the licence (`LICENSE.md`) and the notices
  of the software it links (`THIRD-PARTY-NOTICES.txt`: LLVM, `mimalloc`, `unordered_dense`, `toml++`,
  `nlohmann/json`, `magic_enum`, `small_vector`, `CLI11` and `GenEx`; on macOS and Windows `zstd`; on Windows `zlib`,
  `libxml2` and `pthreads4w`). It replaces the bare `spp-<version>-<label>` binaries. The names carry no version, so
  `releases/latest/download/spp-<label>.zip` always names the newest; `SHA256SUMS` and the attestation cover the zips.
  An unpacked `spp` keeps its executable bit, and the zips' bytes depend only on what is in them.

## CI

- **The codegen checks run on every lane:** each check names the platforms it runs on (`# platforms:`), Linux alone
  when it does not, and `tests/codegen/run.sh` skips the rest, listing them. macOS and Windows run
  `check-self.sh` (install, update and uninstall, including Windows' renaming of a running `spp.exe`); the rest stay
  Linux's for now.

- The Windows lanes no longer list `pac_ret` and `split` as off: the compiler leaves them out itself (see Hardening).

- Downloads and installs in the setup scripts retry (`.github/scripts/lib/retry.sh`), so a flaky mirror or a refused
  endpoint no longer fails the run.

- The post-merge SonarQube job is given the `security-events` and `actions` permissions it needs to upload.

## Internals

- New `spp.codegen.llvm_debug` owns the debug info: `StartDebugInfo`, `FinishDebugInfo`, `AttachSubprogram` and
  `SetDebugLocation` for lines; `DebugTypeOf` (a type once per module) and `DeclareVariable` for variables;
  `EnterDebugBlock` and `LeaveDebugBlock` around each block, a lexical block placed in its function's innermost one (a
  closure's body is generated inside its parent's); and `EndVariable` at a move and `ResumeVariable` where a
  binding is given a value, for a binding that can be moved (neither `Copy` nor a borrow), which is described by
  `#dbg_value`s of its slot rather than a `#dbg_declare`. `LlvmCtx` holds the module's `DIBuilder`, compile unit,
  files, project root, debug types and open blocks; `LlvmVarSymbolInfo` a movable binding's variable. The language is
  `DW_LANG_Rust` until S++ has a registered code: debuggers then read the variables at all (lldb shows none for an
  unknown language) and show tuples, numbers and variants Rust's way. The debug info has no `.debug_names`: coroutine
  splitting names its parts in a way the index would list against entries with no name.
- New `spp.codegen.llvm_lines` builds the source-line table from `spp.o` with LLVM's `DWARFContext`, keyed by each
  function's symbol name and an offset into it, so the S++ functions are never named from IR (taking their addresses
  would give each one a BTI landing pad). Each code section is given its own load address before reading, as every
  section of an object starts at 0 and LLVM finds a compile unit by address alone. Checked against `llvm-symbolizer`
  at every instruction of a test project, at `dev` and `rel`.
- `ErrorFormatter` keeps a line-start table per file, and `LineColOf` answers a position's line and column from it; its
  quoting and spans read the same table.
- `KeySpec::Choices` lets a string key list its allowed values, checked when `spp.toml` is read; `features::LeaveOut`
  is honoured by `IsEnabled`, so a key left out reads as off everywhere.
- The compiler links LLVM's `DebugInfoDWARF` library, and the `llvm` wrapper module exports `DILexicalBlock`,
  `DILocalScope` and `DW_OP_deref`.
- `ty` (pre-commit) leaves out any `vcs/` folder, so a local project's fetched std, whose formatters import `gdb` and
  `lldb`, is not type-checked as the compiler's own code.
- New codegen checks: `check-debug-info.sh`, `check-debug-formatters.sh`, `check-debug-scopes.sh`,
  `check-debug-moves.sh`, `check-info-executable.sh`, `check-self.sh` and `check-run-args.sh`. `lib.sh`'s
  `build_project` passes any further arguments to `spp build`; `check-debug-formatters.sh` takes `STD_ETC` to check
  formatters not yet in SPP-STL. `check-packs.sh` reads a function's parameters with its debug attachment, and
  `check-reproducible.sh` passes with debug info on.
- New gtest suites: `test_msc_source_positions.cpp` and `test_msc_target_facts.cpp`.
